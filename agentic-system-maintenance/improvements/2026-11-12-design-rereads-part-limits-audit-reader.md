# Kit improvement report: design re-reads in the review step, the Copilot CLI part size, and the OpenCode reader the audit digest lacks

- Date: 2026-11-12
- Kit version: 7.0.0
- Clients: Copilot CLI (usage recorded); OpenCode (usage recovered from the client's SQLite session database, which the audit skill does not read)
- Sessions audited: 2, on 1 issue; workflows: DESIGN, both halted at a developer review gate (one at the start of step 9 of 10, one at the end of step 8 awaiting approval; both designs in Draft)

## Findings

### 1. No served step names the `design-snapshot` review read modes, so every correction re-reads the whole design

- Class: workflow (the runtime already provides the modes; the instruction never points at them)
- Where: `workflows/design/08-design-review.md` lines 35 and 89; the same whole-read wording in the tool table of `workflows/design/07-operations.md:29`, `06-filesystem.md:30`, `09-implementation.md:13` and `10-terminal-handoff.md:20`. The modes themselves are documented in `contracts/projections.md`, `#capability:design-snapshot` (`section`, `ids`, `fields`, `grep`, `brief`).
- Evidence: measured counts and sizes, judged cause. Two sessions ran the same workflow on the same issue with the same kit, and they diverge exactly here. In the Copilot CLI session the main conversation received 121 `design-snapshot` answers totalling 597,768 characters across 30 turns — 41% of the 1,450,460 characters it received in the whole run, and the largest response type by a factor of two (the next type is 296,482). The calls cluster into about eight whole-design reads: 10 calls in the contracts step, 26 at the filesystem/operations boundary, 17 and 14 in the operations step, 25 and 8 in the review step, 8 in the implementation step. Not one call carried `fields`, `grep` or `brief`: every read was `section` plus `part` 1..N, at about 6.5k characters per part. In the OpenCode session, on a larger design (85 obligations against 69), the whole run made **2** `design-snapshot` calls totalling 2,609 characters: the index at job activation and one `--section` read during the review. Its review step then corrected the design through drafts in six write calls. The two steps concern the same instruction text, which says only "Re-read the current design": one agent reads the design eight times, the other twice, and nothing in the instruction tells them apart. `contracts/projections.md` already records the same pattern from an earlier measured run ("54 design reads, 206 KB, to review its own design"), which is why the modes exist; the instruction that would make an agent reach for them names none of them. The Copilot CLI review step alone made about 13 design writes, each preceded by a whole read.
- Seen in: both sessions, measured — one read the design eight times, the other twice; the wording is shared by five steps, so systemic by construction.
- Cost: 597,768 characters measured in one session against 2,609 in the other on the same step of the same workflow; halving the type saves a modelled 414,032 weighted input-equivalent tokens (10.2% of that run, which recorded 4,065,046 against 2,113,141 in the other). A per-correction read of one section with `grep` + `fields` + `brief` answers in a few hundred characters where a whole read is 60-75k.
- Proposed change: in `08-design-review.md` line 35 keep the whole read for "Before the adversarial analysis" and make the per-correction entry scoped: "Before every correction: `design-snapshot` with `grep` on the text, id or symbol the correction names, `fields id,<the field you will rewrite>` and `brief`, adding `ids` when the row is already known. Read the whole design again only on the final pass." Line 89 keeps the cold read unchanged. Steps 05-07, 09 and 10 get the same one-line rule beside their `design-snapshot` row, whose purpose reads "Re-read the current design once for the step; a correction reads only its section and rows".
- Flow check: the cold whole read at the start of the review, the final pass, the structural checks, the verifier and the approval gate all stay. Only the per-correction read narrows, and every row it needs stays readable by `id`. No step, check, verifier or approval gate is removed, weakened or reordered.
- To reproduce: run a DESIGN job to the review step on a design of 60 or more obligations, then count `design-snapshot` calls carrying `part` against those carrying `fields`, `grep` or `brief`.

### 2. The GitHub Copilot client has no part size and sends no client id, so every instruction is split and fetched in parts

- Class: runtime
- Where: `config.json`, `partLimit` (7000) and `partLimits` (entries for `claude-code` and `opencode` only, both 24000); and the served role file for GitHub Copilot, `sd-orchestrator.agent.md`, which names no `--client`, while the Claude Code and OpenCode role files pass `--client claude-code` and `--client opencode`.
- Evidence: measured. The same nine DESIGN instructions were served in 10 calls / 149,363 characters to OpenCode (24,000-character parts), five of those calls a single answer of 14,342 to 23,685 characters, and in 38 calls / 199,059 characters to Copilot CLI, 28 of them carrying `--part` (140,775 characters, 71% of that traffic). One instruction was served in 10 parts because its parts were re-served after a compaction. The call gap runs through the whole run: 79 tool calls in the OpenCode main conversation against 491 in the Copilot CLI one, of which 121 were `design-snapshot` part fetches (finding 1) and 28 instruction-part fetches.
- Seen in: 1 of 2 clients, by construction systemic for that client: no `partLimits` entry and no client id.
- Cost: 28 extra calls and 140,775 characters of instruction traffic, plus the turns that carry them; not separable into tokens with the replay.
- Proposed change: add a `partLimits` entry for the Copilot CLI client at the largest single result it passes uncut (18,974 characters in the earlier report; 24,000 matches the other two clients), have the Copilot role file pass `--client copilot-cli` on every runtime call, and keep 7,000 as the default for unknown clients.
- Flow check: only the size of each served part and the client id change. Every instruction and document is still served whole and in order; no step, check, verifier or approval gate is touched.
- To reproduce: run a step whose instruction exceeds 7,000 characters on Copilot CLI and count calls carrying `--part`; run the same step on a client with a 24,000 entry and compare call counts and characters.

### 3. The audit digest reads only Claude Code and Copilot CLI transcripts, so an OpenCode session is reported as having no usage

- Class: runtime (kit tooling: the audit skill's scripts)
- Where: `improve-orchestrator-system` skill, `scripts/digest.mjs`: `transcriptFolders()` searches `~/.claude/projects` and `~/.copilot/session-state` only, and `locate` prints "OpenCode keeps its sessions in its own database, which this script does not read".
- Evidence: measured. For one audited session `locate` found no transcript and `digest` reported usage unavailable, so the session stayed out of the cost ranking and no cause could be attributed to it; the audit could reason only from the session store. The client's own SQLite database (`~/.local/share/opencode/opencode.db`) held the entire run: `session_v2` with `tokens_input` 232,074, `tokens_output` 69,244, `tokens_cache_read` 8,804,352 and `cost`; `session_message` with one row per message carrying the tool name, its input and its full result text; `parent_id` linking nine subagent conversations. Opened read-only, it reproduced every figure the digest needs: 73 main turns, 79 tool calls, per-type result sizes, no failed call in the main conversation, 1 `--help` probe, and a step table cut at `workflow-step-next`. That session proved to be the cheaper of the two (2,113,141 weighted against 4,065,046) and the one whose record carries the evidence of finding 1.
- Seen in: 1 of 2 audited sessions; every OpenCode run.
- Cost: not measured in tokens; one whole session of evidence is lost, and with it in this audit the cross-client comparison behind finding 1.
- Proposed change: add an OpenCode reader to `digest.mjs`. `locate` scans `session_v2` joined with `session_message` for messages whose tool input names the target session id; `load` maps the `session_v2` token columns and the `session_message` tool calls into the same shape `parseCopilot` returns (`turns`, `responses` with `type`, `chars`, `spilled`, `failed`, `input`, `afterTurn`), with `parent_id` children as their own conversations, opening the database as `file:…?mode=ro`. A missing database reads as "no transcript". `summarize`, `replay` and the step table then work unchanged.
- Flow check: evidence collection only. It changes which transcript the audit starts from; no served step, check, verifier or approval gate is touched, and the digest still only reads.
- To reproduce: run `digest.mjs locate --repo <dir> --session <id>` for a session produced by OpenCode, then compare the result with the rows in `~/.local/share/opencode/opencode.db`.
