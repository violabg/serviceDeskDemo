# Repository Context Boundaries

This contract owns the target layout, ordinary-context exclusions, and legacy layout migration. Bootstrap and Maintainer use it together with `contracts/platform-compatibility.md`; platform facts and authentication procedures remain in that compatibility contract.

## Three Separate Areas

Create `knowledge/` at the project root. Place the generated knowledge index at `knowledge/knowledge-index.md` and new project knowledge beneath that root. Its contents describe repository code, domain rules, architecture, testing, and operating conventions. Existing authoritative project documentation may remain in its current location and be referenced by the index; do not relocate it just to populate the folder. Resolve an existing file/directory collision before generation.

Keep active agents, repository skills, instructions, binding files, and schemas outside the maintenance area, in shared or environment-native runtime locations verified for the selected clients. A schema used by Planner or Tester is a runtime resource, even if Bootstrap generated it. Runtime copies must never load a pristine baseline or source-template snapshot as their operating contract.

Use a dedicated top-level `.agentic-system-maintenance/` directory for generated maintenance evidence. An explicitly approved alternative must also be a separate top-level folder, disjoint from knowledge, runtime discovery roots, application documentation, and sessions. Record the resolved path in `MAINTENANCE_ROOT`. Store the manifest, answers, `.baseline/`, source and changelog snapshots, preservation and context-audit plans, research and authentication setup evidence, customization history, and maintenance plans/reports there. Only this generated maintenance evidence moves into the maintenance area; do not put it in `knowledge/`, a runtime instruction/skill tree, or the domain glossary.

Installed Bootstrap/Maintainer skill folders, including their complete skill bodies and resources, stay intact at their installed paths. Do not move them into the maintenance area, truncate them, or replace them with stub entrypoints. Record their paths as maintenance-only excluded roots and exclude them from ordinary reading, search, discovery, indexing, summarization, and delegation. Explicit maintenance invocation loads the complete installed skill and its resources. Verify the selected client's discovery and loading behavior; if ordinary requests eagerly load these files and the client provides no way to prevent that, report context isolation as blocked or unverified. File separation alone is not a guarantee.

## Ordinary Requests

Generated root instructions and every selected runtime role/skill must exclude the maintenance root and other recorded maintenance-only locations from ordinary reading, repository search, discovery, indexing, summarization, and delegation. Pass the exclusions to discovery delegates and to repository-search/knowledge bindings. Use documented search exclusions or bounded searches outside those roots; a broad search followed by discarding maintenance matches has already loaded unwanted context. Remote knowledge operations remain available through approved per-role bindings. Remote catalogs or indexes must filter maintenance material before returning it; if they cannot, use an approved bounded source or report that retrieval route unavailable.

Initial Bootstrap may create and verify the area. After installation, access requires an explicitly requested agent-system maintenance workflow (`upgrade`, `evolve`, or `audit`). General questions about the project or its agent workflow, routine knowledge updates, and application implementation do not activate maintenance. Root instructions carry a short locator and this guard, not maintenance details. A runtime agent that changes a system file reports that provenance needs maintenance; it does not read or refresh the maintenance ledger during the ordinary task.

Knowledge Builder creates/refines only project knowledge and must never scan or index installation records, maintenance resources, duplicate baselines, or template snapshots. Ask follows the same exclusions. Knowledge entries may reference existing project docs, but not maintenance artifacts or maintenance skill bodies. Moving or linking a maintenance file elsewhere does not turn it into project knowledge; exclude aliases and symlink targets too. Do not create a knowledge entry that summarizes excluded content.

## File Plan And Verification

Before approval, classify every proposed file as `runtime`, `knowledge`, `maintenance`, or `maintenance-entrypoint`, list its loaded references, and identify all maintenance-only locations. Ordinary runtime references must stay outside excluded roots; a root router or minimal native entrypoint may declare a maintenance-only reference with an explicit invocation guard. Verify automatic instruction loading, native skill discovery, knowledge retrieval, and bounded searches for every selected client. In an isolated fixture, ordinary Ask/Planner/Knowledge Builder requests must not load maintenance contents; an explicit maintenance request must resolve its complete skill and resources. Record method, result, date, and limitations rather than assuming a hidden directory is ignored.

Knowledge-index Path cells use repository-relative paths in plain text, backticks, or inline Markdown links. Record local project sources in that index; remote knowledge operations retain their approved bindings and source boundaries.

Write a separately approved context audit plan under the maintenance root and run `node <bootstrap-skill>/scripts/verify-context-boundaries.mjs <target-repo-root> <context-audit.json>`. The version-1 plan has `knowledge_root: "knowledge"`, `knowledge_index`, `maintenance_root`, `excluded_roots` (including the maintenance root and any other local maintenance skill roots), `outputs` (the complete approved generated-file and loaded-dependency inventory, excluding baseline snapshot companions), `files`, and `knowledge_entries` (every repository-relative path linked by the generated index). Each file has `output`, `kind`, and `references`; each reference has `output` and `when: "ordinary" | "maintenance"`. Root routers/native maintenance entrypoints with guarded maintenance references set `maintenance_router: true` and record native loading evidence separately. Existing runtime dependencies may be included for inspection without adding them to the answers generated-output list. Knowledge entries outside this audit inventory may be existing project docs. Self-contained maintenance inventories and verification reports are evidence, not runtime dependencies.

The static verifier checks declared coverage, actual index links, physical paths/aliases, folder separation, and loaded-reference boundaries. It cannot prove the meaning of prose, completeness of undisclosed discovery paths, search-service filtering, or native invocation guards. Pair it with preservation, environment-binding, and native loading checks. Baselines of maintenance records must exclude the baseline directory itself: store one pre-baseline copy per generated output, never recursively snapshot `.baseline/` or fabricate answers entries for snapshot copies.

## Legacy Layout Migration

Existing systems may mix knowledge, runtime resources, and provenance under `docs/agents/` or a shared canonical root. During explicit maintenance, detect the recorded locations first, including legacy manifests/answers and installed skill roots. Classify files by purpose and consumers; do not move or exclude an entire mixed directory that still contains active runtime schemas or project docs. Audit mode reports the proposed split without writing.

For approved upgrades/evolution, plan old-to-new paths, collision handling, merge outcomes, and rollback before any move. Preserve the old answers, pristine baselines, source hashes, and customization register as comparison inputs; moving customized files is not permission to recreate BASE from MINE. Re-key per-file slot maps, generated/baseline pairs, adapter loading paths, preservation/environment/context plans, index links, root routing, manifest/snapshot paths, and resource references together. Recompute plan hashes after relocation and verify the generated result before refreshing baselines. Move only generated project knowledge and its index into `knowledge/`; keep existing authoritative project docs in place unless separately approved.

Do not retain ordinary redirects into the maintenance area, blindly remove old mixed roots, or delete a source still used by a selected environment. Restore the prior coherent paths/records if migration fails. A deferred split remains a recorded contract gap; it must not advance the applied-through version past a mandatory unresolved isolation change.
