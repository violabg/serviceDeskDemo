# Implementation Plan Schema

Use this schema for generated Planner agents when they produce the implementation plan that gates code work. It is preserved here as reusable skill reference material.

Schema adherence rules:

- Load this file immediately before drafting or repairing an `implementation-plan.md` artifact.
- The generated plan must follow the four-section structure below. Every section is mandatory.
- Preserve the linked Filesystem Tree, File Details anchors, and backlinks in the generated artifact.
- The `<a id="..."></a>` anchors are intentional schema content. Do not remove or replace them to satisfy markdown diagnostics such as inline-HTML warnings.
- If markdown tooling conflicts with this schema, report or waive the diagnostic after schema validation passes. Schema compliance wins over lint cleanup.
- Before asking for approval or handing off to an Implementor, verify that every Filesystem Tree link points to a matching File Details anchor and that every File Details entry links back to the tree.

## Example for SECTION 1 - Design Overview

````text
## SECTION 1 - Design Overview
- **Starting point:** The existing `IOrderRepository` (domain layer) and `OrderController` (API). A `SendGrid` client is already registered in DI as `IEmailSender`.
- **Features to implement:**
  - Send a notification email when an order's status changes to "Shipped".
  - Handle email delivery failures without blocking the main operation (fire-and-forget with error logging).
  - Include order details (ID, customer name, tracking number) in the email body.
  - Compose the email message through a dedicated `IOrderNotificationComposer` so the format can be changed independently.
- **End state:** Every order status transition to "Shipped" triggers an asynchronous email, and failures are logged without affecting the HTTP response.
- **How I get there:**
  - Create `IOrderNotificationComposer` and its implementation.
  - Modify `OrderController.ShipOrder` to call the new service.
  - Register the new classes in the DI container.
- **Constraints satisfied by the implementation:**
  - Layers: new interface in Domain, implementation in Application.
  - DI: automatic registration via convention (classes ending with `Service`).
  - Error handling: fire-and-forget with `ILogger<OrderNotificationService>` for fallback.
- **Required session artifacts:**
  - `<artifact_name>`: Email template design (an attached image with the desired email format and placeholders).
  - `<artifact_name>`: API endpoint documentation (an attached image showing the API contract for the `ShipOrder` endpoint).
````

Rules for Section 1:

- The feature list must be exhaustive. Every distinct functional aspect must be a separate bullet.
- Use precise existing class or interface names; do not invent names that do not exist.
- The `How I get there` bullets must correspond 1:1 to the files that later appear in Section 3 and, when Section 4 contains executable steps, to those operations as well.
- No vague summaries.

Rules for Section 2:

- Every file leaf contains only the file name as a clickable link, immediately followed by its change type in parentheses.
- The link text must be exactly the file name and the link target must match the file-detail anchor defined in Section 3.
- No autogenerated files appear in this tree.
- Use spaces only for indentation; never tabs.
- Each folder or file occupies its own line. Do not collapse leaves into a compact inline list.
- Show only `NEW`, `MODIFIED`, or `DELETED` files, plus `UNMODIFIED` only when the request is specifically to plan unit tests for existing production code without production edits.

## Example for SECTION 3 - File Details

Code blocks and diff rules:

- Never indent code blocks or diff blocks, even when they follow a bullet label.
- For modified files, each diff zone must be preceded by its own bullet label and then a flush-left `diff` block.

````text
### src/Domain/Contracts/IOrderNotificationComposer.cs

**Role:** Defines the contract for building notification email messages, decoupling the message format from the sending logic.

namespace OurApp.Domain.Contracts;

**Logic to implement (functional recap):**
- **BuildShippedNotification** - Produces an `EmailMessage` with a fixed subject and a body that includes the order ID, customer name, and tracking number.

**Coverage Scenarios:**
None

**Constraints and notes:**
- No dependencies on external services; pure data composition.
- Keep the method signature slim to allow easy testing.
````

Representative modified-file example:

````text
### src/Application/Services/OrderService.cs
<a id="file-OrderService-cs"></a>

**Role:** Orchestrates order status transitions and now triggers a shipment notification.

**Code sections:**
- **Structural diff - using directives**
```diff
+ using OurApp.Domain.Contracts;
+ using Microsoft.Extensions.Logging;
```
- **Zone 1 - Constructor**
```diff
  public OrderService(IOrderRepository repo, IEmailSender sender)
  {
      _repo = repo;
      _sender = sender;
+     _composer = composer;
+     _logger = logger;
  }
```
- **Zone 2 - Method `ShipOrder`**
```diff
  public async Task ShipOrder(int orderId, string trackingNumber)
  {
      var order = await _repo.GetByIdAsync(orderId);
      order.MarkAsShipped(trackingNumber);
      await _repo.UpdateAsync(order);
+     _ = Task.Run(async () =>
+     {
+         try
+         {
+             var customer = await _customerRepo.GetAsync(order.CustomerId);
+             var email = _composer.BuildShippedNotification(order, customer, trackingNumber);
+             await _sender.SendAsync(email);
+         }
+         catch (Exception ex)
+         {
+             _logger.LogError(ex, "Failed to send shipment notification for order {OrderId}", orderId);
+         }
+     });
  }
```

**Logic to implement (functional recap):**
- **Constructor:** Accepts `IOrderNotificationComposer` and `ILogger<OrderService>` injected via DI.
- **ShipOrder:** After persisting the status change, starts a fire-and-forget task that composes and sends the email. Any exception is caught and logged without rethrowing, preserving the original method's response.

**Coverage Scenarios:**
| Test name scenario | Description |
|--------------------|-------------|
| ShipOrder_OrderMarkedAsShipped_TriggersNotificationDispatch | Covers the happy-path business rule that a persisted shipment transition starts the notification dispatch flow after the order state is updated. |
| ShipOrder_PersistingStatusFails_DoesNotStartNotificationDispatch | Covers the failure branch that if persisting the shipped state fails, the method stops before starting the fire-and-forget notification flow. |
| ShipOrder_NotificationDispatchThrows_LogsErrorAndPreservesPrimaryOperation | Covers the resilience branch that any exception inside the fire-and-forget notification flow is caught and logged without changing the outcome of the main shipment operation. |

**Constraints and notes:**
- The fire-and-forget pattern uses `Task.Run` to avoid blocking the HTTP context.
- The `ILogger<T>` must be registered in DI for `OrderService` to compile.

[← Back to Filesystem Tree](#section-filesystem-tree)
````

Rules for Section 3:

- Each file subsection must have a plain-text heading followed immediately by its anchor tag on the next line.
- The content must always contain `Role`, `Code sections`, `Coverage Scenarios`, and may omit `Logic to implement` only when no new business logic is introduced.
- `Coverage Scenarios` must appear immediately after `Logic to implement` when that section is present. If `Logic to implement` is omitted, the `Coverage Scenarios` body must be the literal `None`.
- For every file detail that contains executable business logic, `Coverage Scenarios` is mandatory and must be derived from the exact code shown in that same subsection.
- The `Coverage Scenarios` body must contain only the exact markdown table `| Test name scenario | Description |` for files with executable business logic, or the literal `None` for files that do not require unit-test coverage.
- Scenario names must follow the unit-test naming convention defined in the project knowledge base. Only if the knowledge base does not define one, use `<class-name>_<method-name>_<scenario>` adapted to the naming conventions of the target language.
- Coverage scenarios must maximize business-logic coverage rather than aiming for total implementation coverage.
- For new files, show the full file content, including imports and declarations.
- For modified files, every code block must be a `diff` block, start at column 1, and show the complete final implementation of each changed method or section.
- For unmodified files, use regular code blocks to show only the existing executable code under test that is needed to derive the coverage scenarios.
- Code shown must be mechanically transcribable. Include all required using, import, include, or export statements.
- Add short comments in the code only when they explain why a non-obvious choice was made.
- The link back to Section 2 must be exactly `[← Back to Filesystem Tree](#section-filesystem-tree)` and must be the last line of the subsection.
- Never use tab characters anywhere; indentation is spaces only.

Coverage Scenarios table shape:

````text
| Test name scenario | Description |
|--------------------|-------------|
| <test_name> | <Describe the expected business behaviors> |
````

## Example for SECTION 4 - Operations and Timeline

````text
## SECTION 4 - Operations and Timeline

| Order | Operation | Depends on | Detailed instructions |
|-------|-----------|------------|-----------------------|
| 1 | Create folder structure | - | Create the folders `src/Domain/Contracts/` and `src/Application/Services/` if they do not exist. |
| 2 | Create `IOrderNotificationComposer.cs` | 1 | Create the file at `src/Domain/Contracts/IOrderNotificationComposer.cs` with the content shown in Section 3. |
| 3 | Create `OrderNotificationService.cs` | 1,2 | Create the file at `src/Application/Services/OrderNotificationService.cs` implementing `IOrderNotificationComposer`. |
| 4 | Modify `OrderService.cs` | 2,3 | Apply the diff changes from Section 3. Then verify that the required imports are present. |
| 5 | Register new services in DI | 3 | In `Startup.cs` or the composition root, add `services.AddScoped<IOrderNotificationComposer, OrderNotificationService>();` if not covered by convention. |
| 6 | Build solution | 4,5 | Run `dotnet build` from the solution root. Confirm zero errors. |
````

Rules for Section 4:

- The table must be in chronological order; each operation's dependencies must reflect the real file and dependency order.
- When introducing new `.csproj` projects, the order must be: create folders, create `.csproj`, add to solution, build, then implement source files.
- For autogenerated files, list the exact generation command but never include those generated files in Section 2.
- `Detailed instructions` must include exact commands or paths and verification steps.
- No vague steps like `implement the handler`.
- If Section 2 contains only `UNMODIFIED` production files for unit-test-only planning, do not emit a step table in Section 4.
- In that unit-test-only case, the Section 4 body must be the literal `No production implementation operations required. This plan only defines unit-test coverage for existing code.`

Absolute rules:

- No placeholders. Code must be real implementation, not conceptual snippets.
- No whole-file dumps in modified-file diffs. Show only the changed zones, but each zone must show the complete method or region.
- Links must be clickable. Every link in Section 2 must point to an anchor defined in Section 3 with exactly the same id.
- Diff blocks must use `diff` and start at column 1. Use `+` and `-` for changed lines; include unprefixed context lines only when they are needed to position the change.
- Regular code blocks must remain clearly associated with their section content.
- No tabs anywhere. Only spaces.
- Include all required using or import statements.
- DI changes must be described even if they seem trivial.
- Unit-test planning belongs only in `Coverage Scenarios`. Do not add unit-test files or unit-test operations to Sections 2 or 4.

Adaptation rule: keep the structure unless the target repository has a stronger equivalent. Modify only what is necessary to fit the real repo workflow, artifact names, validation tools, or approval model.
